# Mobile Repository Audit

Verification baseline used for this audit:
- `xcodebuild -project UDIE.xcodeproj -scheme UDIE -sdk iphonesimulator -configuration Debug build` succeeded.
- `flutter analyze` in `udie_mobile/` reported `No issues found!`.
- `npm run build` in `engine-backend/` succeeded.
- `./.venv/bin/pytest -q` in `udie_backend_py/` passed `11` tests.

## 1. Critical Issues

- The native iOS target requests location permission at startup in `LocationManager.requestPermission()` but the shipping plist does not declare `NSLocationWhenInUseUsageDescription`. Evidence: `UDIE/Core/Services/LocationManager.swift:24-26` calls `requestWhenInUseAuthorization()` and `startUpdatingLocation()`, while `UDIE/Info.plist:4-44` contains no location usage string. On device this is a runtime termination vector, not a cosmetic issue.
- The native iOS route-risk path is contract-broken against the current Nest backend. `UDIE/Core/Models/RouteRiskDTO.swift:13-16` expects `{ score, level, eventCount }`, but `engine-backend/src/modules/risk/risk.service.ts:38-43` and `88-94` return `{ riskScore, riskDensity, routeLengthKm, latencyMs, cellCount }`. `UDIE/Features/Map/MapViewModel.swift:167-188` immediately decodes and consumes the incompatible shape, so a successful `200` response still fails in the client.
- The native iOS event feed is contract-broken against the current Nest backend enum surface. `UDIE/Core/Models/GeoEvent.swift:35-55` only accepts lowercase/raw values like `accident`, `construction`, `heavy_traffic`, while `engine-backend/src/common/enums/event-type.enum.ts:1-8` emits uppercase values such as `ACCIDENT`, `CONSTRUCTION`, `HEAVY_TRAFFIC`, `ROAD_BLOCK`, and `WATER_LOGGING`. `UDIE/Core/Networking/APIClient.swift:113-169` decodes events directly into `GeoEvent`, so `/events` responses from the Nest engine will fail decoding.
- The native iOS city dashboard path is contract-broken against the current Nest backend. `UDIE/Core/Models/CityIntelligenceDTO.swift:11-20` maps `avgRisk` and `maxRisk` from `avg_risk` and `max_risk`, but `engine-backend/src/modules/city-dashboard/city-dashboard.service.ts:38-41` returns camelCase `avgRisk` and `maxRisk`. `UDIE/Core/Networking/APIClient.swift:222-254` decodes this DTO directly, so `HomeViewModel.refreshData()` and `CityDashboardViewModel.refresh()` are vulnerable to decode failure.
- The native iOS risk-snapshots path is contract-broken against the current Nest backend. `UDIE/Core/Models/CityIntelligenceDTO.swift:64-65` expects `{ snapshots: [...] }`, while `engine-backend/src/modules/risk-snapshots/risk-snapshots.controller.ts:11-13` returns the raw array produced by `engine-backend/src/modules/risk-snapshots/risk-snapshots.service.ts:33-37`. `UDIE/Core/Networking/APIClient.swift:268-301` decodes the wrapped object, so timeline snapshot fetches fail after HTTP success.
- The Flutter Android release target cannot reach the network because `android.permission.INTERNET` is only declared in debug/profile manifests. Evidence: `udie_mobile/android/app/src/main/AndroidManifest.xml:1-45` has no `<uses-permission>`, while `udie_mobile/android/app/src/debug/AndroidManifest.xml:1-6` and `udie_mobile/android/app/src/profile/AndroidManifest.xml:1-6` define `INTERNET`. This creates a release-only runtime connectivity failure.
- The repository contains two mobile clients and two backend implementations with incompatible runtime assumptions. The native iOS app defaults to `http://localhost:3000` via `UDIE/Info.plist:42-43` and `UDIE/Core/Networking/APIClient.swift:33-60`, while the Flutter app defaults to `127.0.0.1:8000` / `10.0.2.2:8000` in `udie_mobile/lib/src/state/app_store.dart:49-56`. The Flutter client also depends on `/news` and `/sources` in `udie_mobile/lib/src/api_client.dart:41-60`, endpoints that do not exist in the Nest backend.

## 2. Architecture Problems

- The monorepo does not have a single authoritative mobile architecture. It currently contains `UDIE/` (SwiftUI iOS), `udie_mobile/` (Flutter cross-platform), `engine-backend/` (NestJS/Postgres), `udie_backend_py/` (FastAPI/SQLite), and an orphaned root Dart infrastructure shard under `lib/infrastructure/`. This is not modularization; it is product duplication with overlapping concerns and no contract ownership boundary.
- The Swift client mixes MVVM naming with presentation-driven service construction. `UDIE/Features/Map/MapViewModel.swift:39-66` instantiates `LocationManager`, `RiskGridService`, and `EventRepository` directly inside the view model; `UDIE/Core/Networking/APIClient.swift` is a process-global singleton; `UDIE/App/UDIEApp.swift` injects `AppState` and `LocationManager` as global environment objects. There is no domain layer mediating these dependencies.
- Global state is duplicated rather than centralized. `UDIE/Core/Models/AppState.swift:5-21` owns `region`, `events`, `snapshots`, `routes`, and selections, but `UDIE/Features/Map/MapViewModel.swift:24-37` defines a second parallel state graph for the same concerns. `UDIE/Features/Map/MapOperationsView.swift:24-47` then keeps a third local copy for `region`, `routes`, and `selectedRoute`. This invites divergence between UI and data-plane state.
- The Swift app has multiple navigation roots. `UDIE/App/AppRouter.swift` establishes a `TabView`, then feature screens such as `UDIE/Features/Home/HomeView.swift:5-71`, `UDIE/Features/CityIntelligence/CityDashboardView.swift:5-119`, `UDIE/Features/Diagnostics/SystemHealthView.swift:4-69`, `UDIE/Features/SystemHealth/HealthOperationsView.swift:4-31`, `UDIE/Features/Route/RoutePlannerView.swift:11-80`, and `UDIE/Features/ScenarioSimulation/ScenarioSimulationView.swift:9-83` each create their own `NavigationView`. This creates conflicting ownership of title bars, dismissal flow, and deep-linking.
- UI, infrastructure, and business logic are tightly coupled in `UDIE/Features/Map/MapOperationsView.swift`. The same type owns map composition, route-card formatting, sync badges, state transitions, route clearing, empty-state handling, and modal orchestration in `:22-220` and the remainder of the file. This is effectively a god view.
- The repository still shows a half-removed Clean Architecture experiment for Dart. `lib/infrastructure/persistence/vital_dao.dart`, `lib/infrastructure/persistence/vital_record.dart`, and `lib/infrastructure/repositories/local_vital_repository.dart` remain, while corresponding root `lib/domain/...` files are deleted in the current worktree. That leaves persistence code without an in-repo domain contract and makes the root `lib/` tree internally inconsistent.
- The backend layer is split-brain rather than environment-tiered. The FastAPI backend exposes `/news`, `/sources`, India-only validation, and SQLite persistence in `udie_backend_py/app/main.py:57-177` and `udie_backend_py/app/storage.py:39-219`; the Nest backend exposes spatial materialization, diagnostics, reliability, users, and route options in `engine-backend/src/main.ts:5-12` and its module tree. There is no gateway, compatibility layer, or generated API contract between them.
- The Swift diagnostics path leaks infrastructure data models directly into UI. `UDIE/Core/Models/CityIntelligenceDTO.swift:68-121` defines an `ArchitectureAuditReport` with `AnyCodable`, and `UDIE/Features/Diagnostics/SystemHealthView.swift:56-69` plus `:116-124` reads nested dictionary values directly in the presentation layer. This bypasses typed domain semantics and makes the UI fragile to backend schema drift.

## 3. Code Quality Problems

- `BoundingBox` is defined twice in the same Swift target tree: `UDIE/Core/Extensions/MKCoordinateRegion+BoundingBox.swift:10-15` and `UDIE/Core/Models/BoundingBox.swift:9-13`. The current Xcode file-system sync exceptions prevent an immediate compile failure, but the repository structure itself is contradictory and one target-membership change will surface a duplicate-symbol compile error.
- `LocationManager` still carries an `Untitled.swift` header in `UDIE/Core/Services/LocationManager.swift:1-6`. That indicates unmanaged file provenance in a production target and correlates with the missing plist permission metadata.
- `MapViewModel` is overloaded and contains transport orchestration, retry sequencing, state semantics, viewport heuristics, snapshot loading, selection state, and local-risk placeholder logic in one class. Evidence: `UDIE/Features/Map/MapViewModel.swift:77-152`, `155-203`, `215-282`. This increases change risk and makes unit isolation difficult.
- `MapOperationsView` uses ad hoc presentation logic instead of view data builders or smaller composable view models. The route recommendation copy, ETA math, and delay estimate are all computed inline in `UDIE/Features/Map/MapOperationsView.swift:87-125`.
- `HealthOperationsView` ships mock operational data inside the main target. `UDIE/Features/SystemHealth/HealthOperationsView.swift:123-137` hardcodes metrics and sleeps instead of calling a real diagnostic source.
- `IntelligenceFeedViewModel` is placeholder logic inside the production app. `UDIE/Features/IntelligenceFeed/IntelligenceFeedView.swift:85-95` sleeps and injects synthetic items instead of calling an API or repository.
- `ScenarioSimulationView` is also placeholder logic inside the main target. `UDIE/Features/ScenarioSimulation/ScenarioSimulationView.swift:86-90` only toggles a local boolean after a delay, while `:101-102` renders hardcoded impact values.
- Test coverage is effectively absent on the client surfaces. `UDIETests/UDIETests.swift:8-15` is an empty template, and `udie_mobile/test/widget_test.dart:1-6` only checks `2 + 2 == 4`.
- The Swift diagnostics DTO uses `AnyCodable` with `[String: [String: AnyCodable]]` in `UDIE/Core/Models/CityIntelligenceDTO.swift:68-121`, which weakens type guarantees and hides schema regressions until runtime.
- The Python backend persists to a checked-in SQLite model with coarse-grained locking. `udie_backend_py/app/storage.py:39-45` creates a single shared SQLite connection protected by one `threading.Lock`, and the repo also includes `udie_backend_py/udie_state.db`. This is deterministic for local testing but poor production hygiene.

## 4. Performance Bottlenecks

- `AnyView` is used at the root of the heaviest Swift screen. `UDIE/Features/Map/MapOperationsView.swift:127-129` type-erases the main body around a large conditional map surface. This prevents SwiftUI from using stronger compile-time diffing on the most stateful screen.
- `ClusteredMapView.updateUIView` performs coarse full-surface replacement. `UDIE/Core/Components/ClusteredMapView.swift:47-70` rebuilds all annotations whenever the signature set changes, `:72-79` tears down and re-adds all route polylines, and `:81-96` removes and recreates all snapshot polygons on any snapshot-set change. That guarantees redraw churn instead of incremental diffing.
- Route-risk evaluation in the Nest backend has avoidable quadratic behavior. `engine-backend/src/modules/risk/risk.service.ts:60-74` iterates every influenced cell and calls `findNearestRouteCell`, which linearly scans every route cell in `:206-217`. The hot path is therefore `O(influence_cells * route_cells)`.
- `MapViewModel.loadEvents()` does a health probe before every event fetch. `UDIE/Features/Map/MapViewModel.swift:106-122` calls `APIClient.shared.healthCheck()` and then separately fetches `/events`. On map panning this doubles network chatter and latency on the main intelligence path.
- The Flutter shell rebuilds the entire home scaffold on any store mutation. `udie_mobile/lib/src/ui/screens/home_shell.dart:22-80` wraps the whole screen tree in `AnimatedBuilder`, so every `notifyListeners()` from `AppStore` repaints the app bar, navigation shell, and all page roots.
- `AppStore.refreshAll()` performs sequential I/O instead of bounded parallelism. `udie_mobile/lib/src/state/app_store.dart:82-105` waits for namespace detection, then events, then news, then sources. This increases wall-clock latency and keeps the UI in `CONNECTING` longer than necessary.
- The Python backend serializes ingestion, lifecycle projection, and rebuild work through a single SQLite connection and one process lock. `udie_backend_py/app/storage.py:109-139`, `141-207`, and `209-219` all execute under the same lock, which will not scale past single-process local usage.
- The Swift route planner triggers geocoding and routing directly from the view on the main actor. `UDIE/Features/Route/RoutePlannerView.swift:233-287` orchestrates geocoding, route calculation, and status-state mutation inline from the UI layer, with no caching or request coalescing.

## 5. Security Risks

- Both mobile clients default to insecure cleartext transport. The native iOS app defaults to `http://localhost:3000` in `UDIE/Info.plist:42-43` and `UDIE/Core/Networking/APIClient.swift:33-60`. The Flutter app defaults to `http://127.0.0.1:8000` / `http://10.0.2.2:8000` in `udie_mobile/lib/src/state/app_store.dart:49-56`.
- The Flutter iOS target disables App Transport Security globally. `udie_mobile/ios/Runner/Info.plist:48-52` sets `NSAllowsArbitraryLoads=true`, which removes ATS protection for all endpoints rather than whitelisting controlled development hosts.
- The Nest backend exposes wide-open CORS. `engine-backend/src/main.ts:6-9` calls `app.enableCors()` with default permissive behavior, and the FastAPI backend explicitly sets `allow_origins=["*"]` in `udie_backend_py/app/main.py:22-29`.
- The users API stores a reversible mock password surrogate. `engine-backend/src/modules/users/users.controller.ts:16-23` takes the raw password and stores `mock_hash_${password}`. This is not hashing and creates immediate credential disclosure risk if the users table is queried or logged.
- There is no visible authentication or authorization boundary protecting administrative or user-management endpoints. `engine-backend/src/modules/users/users.controller.ts:7-37` exposes list/create/update/delete operations without guards; `engine-backend/src/modules/diagnostics/diagnostics.controller.ts:4-32` exposes architecture audit and rebuild-determinism endpoints the same way.
- The shared Xcode scheme leaks environment-specific infrastructure into versioned project metadata. `UDIE.xcodeproj/xcshareddata/xcschemes/UDIE.xcscheme:76-81` stores a concrete LAN IP (`http://172.25.232.49:3000`) in a shared scheme, which is a configuration leak and a reproducibility hazard for other developers and CI.
- The Flutter Android release configuration is signed with the debug key. `udie_mobile/android/app/build.gradle.kts:33-38` binds `release` to `signingConfigs.getByName("debug")`. That is not only a distribution problem; it also weakens integrity guarantees for any release artifact.
- The Nest ingestion layer sends bearer credentials directly to the OpenAI API with no secrets boundary beyond process env. `engine-backend/src/modules/ingestion/social-event-parser.service.ts:30-31` loads `OPENAI_API_KEY`, and `:73-79` sends it as a live bearer token. There is no secret manager abstraction, no egress policy control, and no documented key scoping in the repo.
- Neither mobile client implements certificate pinning or host allow-list enforcement. The Swift client resolves any base URL from env or plist in `UDIE/Core/Networking/APIClient.swift:40-60`, and the Flutter client accepts arbitrary operator-entered backend URLs via `udie_mobile/lib/src/ui/screens/sources_screen.dart` and `AppStore.updateBaseUrl()` in `udie_mobile/lib/src/state/app_store.dart:188-191`.

## 6. Scalability Risks

- The repository is region-hardcoded to India and frequently to Delhi. Evidence includes `udie_backend_py/app/main.py:195-240` and `229-240` for India-only validation, `udie_mobile/lib/src/state/app_store.dart:10-38` for allowed cities, and repeated Delhi defaults in `UDIE/Features/Map/MapOperationsView.swift:43-45`, `UDIE/Features/Home/HomeViewModel.swift`, and `UDIE/Features/Route/RoutePlannerView.swift:44-47`. This blocks multi-city and multi-tenant rollout.
- Both mobile clients replace full collections instead of diffing paged data. `udie_mobile/lib/src/state/app_store.dart:93-105` swaps entire `events`, `news`, and `sources` lists; `UDIE/Features/Map/MapViewModel.swift:122-137` replaces `events` wholesale. There is no pagination contract on the Swift side and only hard-coded limits on the Python side.
- The Flutter backend profile is structurally single-node. `udie_backend_py/app/storage.py:39-45` uses one SQLite connection; `:109-219` serializes projection logic behind one lock; `udie_backend_py/README.md` documents SQLite as the deployment profile. This will not scale to multi-worker mobile traffic or sustained source ingestion.
- The Nest backend and Python backend model the same product differently. The Flutter app depends on area-news and source-diagnostics semantics from `udie_backend_py/app/main.py:57-177`, while the Swift app depends on city dashboard, diagnostics, and risk snapshots from the Nest backend. Teams cannot scale feature delivery when there are two incompatible truth surfaces.
- `AppState` and `AppStore` are unbounded mutable singletons from the perspective of UI trees. `UDIE/Core/Models/AppState.swift:5-21` and `udie_mobile/lib/src/state/app_store.dart:58-76` keep entire in-memory collections for events/news/sources/routes without eviction or persistence strategy.
- The Python backend rebuild endpoint is synchronous and destructive. `udie_backend_py/app/main.py:170-173` and `udie_backend_py/app/storage.py:209-219` rebuild active state by deleting and recreating projections on the request path. This does not survive scale or concurrent users.
- The Swift local-risk path is placeholder client-side computation. `UDIE/Features/Map/MapViewModel.swift:271-281` averages mock H3 keys. If this path graduates without being removed, it will embed backend logic into the client and fragment scoring semantics.

## 7. Recommended Refactoring

- Priority 1: Problem: the native iOS app has multiple runtime contract failures and one permission-triggered crash path. Root cause: mobile DTOs and plist metadata are drifting independently from the backend contracts and platform requirements. Concrete fix: add `NSLocationWhenInUseUsageDescription`; replace `RouteRiskResponse`, `GeoEvent`, `CityDashboardResponse`, and `RiskSnapshotsResponse` with DTOs generated from the active backend; add contract tests that decode real fixture payloads from `/events`, `/risk`, `/city-dashboard`, and `/risk-snapshots`.
- Priority 1: Problem: Flutter Android release builds cannot talk to the backend. Root cause: `INTERNET` permission is scoped to debug/profile only. Concrete fix: move `android.permission.INTERNET` into `udie_mobile/android/app/src/main/AndroidManifest.xml`, add a release smoke test, and verify a signed release artifact can perform `/api/health`.
- Priority 1: Problem: the repository has no single authoritative backend/client pairing. Root cause: Swift targets the Nest API surface while Flutter targets the FastAPI surface, and both are checked in as first-class apps. Concrete fix: choose one supported mobile/backend matrix per deployment profile, mark the other stack experimental or legacy, and enforce ownership in the root README plus CI workflows.
- Priority 2: Problem: Swift state is split across `AppState`, `MapViewModel`, and local view state. Root cause: no explicit separation between app shell state, screen state, and domain state. Concrete fix: move map state into one source of truth, inject repositories/services through constructors, and keep screen-specific transient state local to the screen coordinator only.
- Priority 2: Problem: production targets contain placeholder features (`HealthOperationsView`, `IntelligenceFeedViewModel`, `ScenarioSimulationView`). Root cause: shell-phase UI scaffolding was committed into the main target without feature flags or separate demo targets. Concrete fix: either back these views with real repositories or move them into a demo/internal build target protected by compile flags.
- Priority 2: Problem: the root `lib/infrastructure` shard is orphaned. Root cause: partial deletion of a prior Dart architecture without deleting or relocating persistence code. Concrete fix: either remove the root `lib/` tree entirely or move it under `udie_mobile/lib/` behind a coherent feature/domain/data structure.
- Priority 3: Problem: users and diagnostics endpoints are unauthenticated and password handling is not real. Root cause: the auth subsystem was never implemented despite a users table and module. Concrete fix: add password hashing with Argon2/bcrypt, remove password echo storage, add auth guards to user/diagnostic/admin endpoints, and restrict diagnostics/rebuild routes to internal roles.
- Priority 3: Problem: cleartext networking and blanket ATS/CORS settings weaken the deployment surface. Root cause: development convenience settings were committed as default runtime behavior. Concrete fix: use HTTPS-only base URLs in production, replace `NSAllowsArbitraryLoads` with scoped ATS exceptions for local dev only, restrict CORS origins per environment, and add backend host allow-listing in both clients.
- Priority 4: Problem: map rendering and route-risk evaluation perform too much work per update. Root cause: coarse overlay replacement on the client and nearest-cell scanning on the server. Concrete fix: incremental annotation/overlay diffing in `ClusteredMapView`, route-cell set precomputation or distance bucketing in `RiskService`, and removal of extra `/health` probes from hot refresh loops.
- Priority 4: Problem: Flutter rebuild granularity is too coarse and network calls are fully sequential. Root cause: `AnimatedBuilder` wraps the whole shell and `AppStore` exposes one global notifier for all concerns. Concrete fix: split store concerns into smaller listenable models or state notifiers, parallelize independent fetches after namespace detection, and rebuild only the active tab content.
- Priority 5: Problem: repository hygiene is poor. Root cause: generated/binary/local-environment artifacts and mutable config are versioned together with source. Concrete fix: stop tracking shared scheme IP overrides, debug signing defaults, SQLite state DBs, `.venv`, caches, and placeholder docs that do not correspond to an owned runtime path.
- Priority 5: Problem: client tests do not protect any critical path. Root cause: template test files were never replaced with repository-specific coverage. Concrete fix: add contract-decoding tests for all DTOs, permission/config tests for plist/manifests, and at least one UI smoke test per app shell.

## 8. Future Upgrade Roadmap

### Short Term (0-4 weeks)

- Select the supported mobile/backend matrix and mark the other stack as experimental or legacy in repository docs and CI.
- Fix iOS permission metadata and repair all Swift DTO/backend contract mismatches.
- Move Flutter `INTERNET` permission to the main manifest and replace release debug signing with a real release signing configuration.
- Remove shared-scheme hardcoded IPs and convert dev-only endpoint overrides to untracked local configuration.
- Add authentication and authorization to user-management and diagnostics endpoints; remove `mock_hash_*` password storage immediately.
- Replace placeholder production views with either live data or feature flags that keep them out of release targets.

### Mid Term (1-3 months)

- Refactor the Swift app into explicit presentation/domain/data boundaries with injected repositories instead of singleton/service construction inside view models.
- Collapse duplicated mobile state containers into a single source of truth per screen/application boundary.
- Introduce generated API contracts or shared schema fixtures between mobile clients and the supported backend to stop drift.
- Replace coarse map overlay replacement with incremental diffing and move any expensive route-risk preprocessing off the request hot path.
- Split the Flutter `AppStore` into smaller feature-specific stores and add persistent cache/offline semantics for recent responses.
- Add real client and backend integration tests for `/events`, `/risk`, `/city-dashboard`, `/risk-snapshots`, `/news`, and `/sources`.

### Long Term (3-9 months)

- Decommission one backend implementation or place it behind a compatibility gateway with versioned contracts.
- Replace the Python SQLite deployment profile with a production-grade persistence layer if the Flutter app remains a supported product.
- Introduce environment-specific configuration packaging for debug/staging/release across both mobile stacks, including secret management and certificate strategy.
- Modularize the mobile product by feature and contract ownership rather than by mixed experiments, with shared design/system packages only where the runtime contract is identical.
- Build a documented multi-city, multi-tenant data model that removes Delhi/India hardcoding from app state, backend validation, seed data, and UI assumptions.
